# Редактирование базы знаний

Схема и пример — в `docs/SPEC.md` §5. Pydantic-модели — в `app/kb/models.py`: они источник правды, SPEC должен с ними совпадать.

## Правила id

- Префикс по типу: `faq.`, `product.`, `policy.`, `rule.`; далее `snake_case`, латиница: `faq.delivery_regions`, `product.bag_15`.
- id не переиспользуются и не переименовываются без поиска по репозиторию (`evals/cases.yaml`, тесты, фикстуры ссылаются на них).

## Правила контента

- Одна запись — один факт или один вопрос. Длинные ответы дробить.
- Цены — числом (`price: 89990`), без форматирования; форматирование делает код.
- В `faq.questions` — 3–6 формулировок так, как пишут клиенты (с опечатками и разговорными словами).
- У каждого товара — `aliases`, чтобы кандидаты допродажи и детектор «уже предлагали» его находили.
- Каждое `upsell_rules[].offer_id` должно существовать в `products`.

## Процедура

1. Внеси правку.
2. Проверь загрузку: `uv run python -m app.kb.validate data/kb` (ошибка = понятное сообщение с id записи).
3. На каждое новое правило допродажи добавь хотя бы один eval-кейс в `evals/cases.yaml` (когда предлагать и когда нет).
4. `/run-evals fake`.

## Конвертация БЗ работодателя

Исходник — в `data/kb/source/` без изменений. Конвертер — `scripts/convert_kb.py`, повторяемый. В README укажи, что было интерпретировано вручную.
