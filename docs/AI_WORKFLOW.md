# Как проект делался с ИИ

Проект целиком написан в **Claude Code** (модель Claude Opus 5.5) под управлением человека: он ставил задачи по этапам, принимал решения по развилкам и проверял результат руками.
Ниже — как устроен процесс, что проверялось и где ИИ ошибался.

## Настройка репозитория под ИИ

| Файл | Зачем |
|---|---|
| [`CLAUDE.md`](../CLAUDE.md) | Правила проекта: стек, слои, 8 инвариантов, конвенции, Definition of Done, процесс по этапам |
| [`docs/SPEC.md`](SPEC.md) | Постановка, контракты, сценарии S1–S10, метрики, этапы M0–M6 с критериями приёмки |
| `.claude/skills/run-evals` | Прогон evals, сравнение с прошлым отчётом, запрет подгонять ожидания |
| `.claude/skills/prompt-change` | Структура промпта, версионирование, обязательный eval-кейс на правку |
| `.claude/skills/kb-edit` | Правила id и контента БЗ, валидация, eval-кейс на каждое правило допродажи |
| `.claude/skills/amocrm-integration` | Проверенные факты об API amoCRM; «не придумывай поля — открой документацию и допиши источник» |
| `.claude/skills/ship-check` | Финальный чек-лист перед сдачей |
| `.claude/agents/tech-lead-reviewer.md` | Субагент «строгий техлид»: только читает и запускает, ищет, за что снизят оценку |
| `.claude/settings.json` | Разрешения (`uv run`, `make`, git без push; чтение `.env` запрещено) и хук: `ruff format` + `ruff check --fix` после каждой правки |

## Процесс

1. **План до кода.** Первым сообщением ИИ прочитал CLAUDE.md и SPEC, задал 4 вопроса по развилкам (материалы работодателя, бюджет времени, аккаунт amoCRM, противоречие «сильный негатив» / «любой negative») и составил план M0–M6: файлы, протоколы, тесты, риски, ADR. Противоречия и неясности SPEC записаны как допущения A7–A21 в README.
2. **Этапы по одному.** Каждый этап — отдельная команда человека: «Реализуй Mn. Сначала тесты на критерий приёмки, потом код. В конце — make check и коммит». Тесты писались первыми и падали до реализации.
3. **`make check` после каждого этапа:** ruff, mypy strict, pytest, порог покрытия 85%. Жёсткие метрики evals на fake входят в тот же прогон.
4. **Маленькие коммиты** в стиле Conventional Commits: один этап — серия осмысленных коммитов (`build:`, `feat(kb):`, `fix(upsell):`, `docs:`).
5. **Проверка в настоящем браузере.** UI прогонялся в headless Chrome через DevTools Protocol, без новых зависимостей: встроенный в Node WebSocket. Сценарий выбирается, нажимается «Отправить», снимаются DOM и скриншоты — в том числе мобильная ширина и проверка XSS.
6. **Ревью субагентом** `tech-lead-reviewer` после M3. Он запускал проект по README и ломал его: инъекции, вопросы вне БЗ, грубость, мусор.
7. **Evals** (`/run-evals`) после изменений БЗ и допродажи. Провалы разбирались по причине, ожидания кейсов не подгонялись.

## Что проверял человек

- Ответил на развилки плана и подтвердил допущения (в том числе «любой `negative` → без допродажи»).
- Прошёл сценарии S1, S4, S7 руками в демо-UI (критерий M3).
- Решил не использовать реальный API модели на этом этапе: ключа нет (допущение A21).

## Где ИИ ошибался и как это ловилось

| Ошибка | Как поймали | Что сделали |
|---|---|---|
| Думал передавать `temperature` в `messages.create`, а в Anthropic SDK 1.x параметр убран из сигнатур (TypeError) | Упал тест адаптера на подменённом HTTP-транспорте | `temperature` — только моделям, которые её принимают, через `extra_body`; уточнено допущение A8 |
| План предполагал «принудительный tool call» из SPEC, но у Opus 5.5 / Sonnet 5.5 он возвращает 400 | Сверка с документацией SDK перед написанием кода | Structured output по JSON-схеме (A7, ADR-003) |
| Регулярка согласия ловила «не **нужна**» как согласие — отказ превращался в интерес | Прогон тест-кейсов отказов до запуска | Отрицательный lookbehind + тесты на «мышку не надо, а сумку давайте» |
| BM25 не находил FAQ по «когда сможете доставить?»: Snowball разводит «доставить» и «доставка» по разным основам | Прогон UI в headless Chrome | Совпадение по корню основы с весом 0.5 + формулировки клиентов в БЗ |
| Пресет S3 «трейд-ин» случайно совпадал с FAQ режима работы («принимаем») | Тот же прогон UI | Пресет заменён на однозначно отсутствующую тему |
| Список сценариев выталкивал кнопку за экран на телефоне, чипы сжимались в овалы | Скриншоты headless Chrome | Правки CSS, повторные скриншоты |
| Проверка шла на старом сервере без `--reload` — UI показывал поведение до правки | Расхождение между CLI и UI | Перезапуск; дальше `make run` с автоперезагрузкой |
| **Ревью техлида, 4 критичных:** вопрос вне БЗ получал уверенный ответ не по теме («доставка на Марс» → доставка по Москве); отказ «гарантия не нужна» не распознавался; грубость не отключала допродажу; фолбэк ловил не все исключения | Субагент `tech-lead-reviewer` ломал демо | Проверка «часть вопроса вне словаря БЗ → уточню», guardrail `unanswered_number`, совпадение упоминаний по корню, расширенный словарь жалоб, фолбэк на любую ошибку. На каждую находку — тест, который её воспроизводит |
| При проверке правок техлида FakeLLM отвечал не по теме при совпадении одного слова («документы» → FAQ для юрлиц) | Ручной прогон обычных вопросов после исправлений | Найденная запись должна покрывать ≥ 50% смысловых слов вопроса |
| Первый прогон evals: ожидания кейсов 81%. Слово «работаете» случайно попало в список типовых, «почём» не было в словаре, пробел в формулировках БЗ, подсказка S6 без политики, неверный приоритет кандидатов | `/run-evals` | Исправлена реализация, ожидания кейсов не менялись → 100% |
| Удаление `KICKOFF.md` попало в коммит про отказы: уже было в индексе | Проверка `git show --stat` после коммита | Пересобраны 4 локальных (не отправленных) коммита |
| В коммите и документе написано «26 кейсов» вместо 27 | Шапка отчёта evals | Исправлен документ; история не переписывалась |
| Допущение «чат без сделки — примечание не пишем» отбрасывало бы даже пример из документации amoCRM (там `element_type=1`, контакт) | Навык требовал сверки с документацией до кода | Примечание пишется в сделку или контакт; коды помечены «проверить на реальном аккаунте» |
| Тест на испорченный payload проходил при любом исходе (сам бросал ожидаемое исключение) | Линтер (PT012) указал на подозрительный блок | Разделён на два честных теста |

## Чему это научило

- **Инварианты — в коде, а не в промпте.** Всё, что ловил техлид, закрывалось детерминированной проверкой с тестом, а не уговорами модели.
- **Ревью от «злого» субагента окупается** — особенно до evals и интеграции, пока исправления дешёвые.
- **Проверять в браузере, а не только API.** Три ошибки из таблицы видны только в живом UI.
- **Документацию внешних API читать до кода.** Два решения (structured output, привязка к контакту) изменились после сверки.
