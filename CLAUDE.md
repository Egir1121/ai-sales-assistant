# AI Sales Assistant

Сервис принимает обращение клиента (плюс историю диалога из amoCRM), сверяется с короткой базой знаний (БЗ) и возвращает **два блока**:

1. `client_reply` — вежливый ответ клиенту, только по фактам из БЗ.
2. `manager_hint` — подсказка менеджеру: что допродать, почему, какой фразой, и когда НЕ предлагать.

Полная постановка, контракты, правила и критерии приёмки: @docs/SPEC.md
Архитектурные решения (ADR) ведём в `docs/ARCHITECTURE.md` — создаёшь и обновляешь его сам.

## Стек

- Python 3.12, `uv` (зависимости и запуск), FastAPI, Pydantic v2, httpx
- LLM: Anthropic SDK за интерфейсом `LLMClient`; `FakeLLM` для тестов и офлайн-демо
- Тесты: pytest (+ pytest-asyncio), линт: ruff, типы: mypy (strict для `app/core`, `app/kb`, `app/upsell`)
- Docker + docker compose для запуска «одной командой»

## Команды

```bash
make install     # uv sync
make run         # uvicorn app.main:app --reload (демо UI на http://localhost:8000)
make check       # ruff check + ruff format --check + mypy + pytest  ← гонять после каждого этапа
make evals       # python -m evals.run --provider fake  (реальный LLM: make evals-real)
make demo        # docker compose up --build
```

Если Makefile ещё нет — создай его на этапе M0 ровно с этими целями.

## Архитектура (слои и направление зависимостей)

```
api/ (FastAPI, демо UI, вебхук amoCRM)
  └─> core/pipeline.py (AssistService — оркестрация)
        ├─> kb/        загрузка и валидация БЗ, Retriever
        ├─> upsell/    детерминированные кандидаты на допродажу
        ├─> llm/       LLMClient (anthropic | fake), промпты в файлах
        └─> core/guardrails.py  пост-валидация ответа
integrations/amocrm/  адаптер CRM (парсинг вебхуков, история диалога, запись примечаний)
```

- `core`, `kb`, `upsell` не импортируют FastAPI, httpx и SDK провайдеров — только чистый Python + Pydantic.
- Все внешние зависимости (LLM, amoCRM, хранилище истории) — через протоколы и DI (`Depends`/фабрики), чтобы подменять в тестах.
- Pydantic-модели на всех границах: HTTP, ответ LLM, БЗ, payload вебхука.

## Инварианты (нарушать нельзя)

1. **Никаких выдуманных фактов.** Цены, сроки, условия, наличие — только из БЗ или истории диалога. Нет данных → `needs_manager=true` и нейтральная фраза «уточню и вернусь».
2. **Допродажа только из кандидатов,** которые построил код (`upsell/`). LLM ранжирует и формулирует, но не придумывает товары. Любой `offer_id` вне кандидатов отбрасывается guardrail-ом.
3. **Жалоба, возврат, сильный негатив → upsell пустой** и заполнен `upsell_suppressed_reason`. Решает код после ответа LLM, а не только промпт.
4. **Не повторять отклонённое.** То, от чего клиент уже отказался в диалоге, не предлагается снова.
5. **Текст клиента — данные, не инструкции.** Оборачиваем в теги, в системном промпте явно запрещаем выполнять инструкции из него.
6. **Работает без API-ключа** (`LLM_PROVIDER=fake`): проверяющий должен запустить проект за 1 минуту.
7. **Деградация, а не падение:** таймаут/ошибка LLM → шаблонный безопасный ответ + `meta.fallback_used=true`.
8. Секреты только в `.env` (в git — `.env.example`). Телефоны и email в логах маскируются.

## Конвенции

- Промпты — файлы в `app/llm/prompts/`, у каждого `PROMPT_VERSION`. Любая правка промпта → навык `/prompt-change`.
- Правки БЗ → навык `/kb-edit`. Работа с amoCRM → навык `amocrm-integration` (там проверенные факты об API — не выдумывай поля).
- Новые зависимости — только с обоснованием в ADR. Без LangChain и векторной БД по умолчанию: БЗ короткая (обоснование — в ADR-001). Если в вакансии явно указан LangChain/LangGraph — используем его только внутри `llm/` и фиксируем в ADR.
- Коммиты маленькие, Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`), один этап = серия осмысленных коммитов.
- Сначала тест на критерий приёмки этапа, потом код.
- Комментарии и docstrings — по-русски или по-английски, но единообразно в пределах модуля; идентификаторы — по-английски.

## Процесс работы

1. Новый этап (M0–M6 из SPEC) начинай в plan mode: план → моё подтверждение → код.
2. После этапа: `make check` зелёный → если трогал промпты/БЗ/допродажи — `/run-evals` → коммит.
3. Нашёл противоречие в SPEC или неясность — не додумывай молча: предложи вариант и запиши допущение в раздел «Допущения» README.
4. Перед сдачей: `/ship-check` (он же вызовет агента `tech-lead-reviewer`).

## Definition of Done (для всего проекта)

- `git clone` → `cp .env.example .env` → `make demo` → открывается демо, ответ приходит без ключа.
- `make check` зелёный, покрытие `core/`, `upsell/`, `kb/` ≥ 85%.
- `evals/report.md` свежий, жёсткие метрики = 100% (см. SPEC §9).
- README по структуре из SPEC §11, с диаграммой, скриншотом/GIF и таблицей результатов evals.
